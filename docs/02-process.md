# Процесс разработки по SDD

## Роли

| Роль | Пишет | Отвечает за |
|---|---|---|
| БА / PO | `proposal.md`, бизнес-`specs/` | что и зачем: проблема, скоуп, сценарии WHEN/THEN |
| Системный аналитик (СА) | `system.md`, `specs/integration/`, `contracts/` | компоненты, матрица сценариев, контракты, логическая модель данных, НФТ, порядок выкатки |
| Техлид компонента | ревью `system.md` и `design.md` | реализуемость, архитектура компонента |
| Разработчик | `design.md`, `tasks.md`, код | реализация, тесты, archive impl-change |
| QA | — | тест-кейсы по сценариям, трассировка |

**Граница СА и команд:** всё, что видно снаружи компонента (API, события, ошибки, обмен
данными, НФТ), решает СА. Всё, что внутри (таблицы, классы, фреймворки), решает команда.

## Жизненный цикл

```
STORE                                          КОМПОНЕНТЫ
1 БА: /sdd-business-propose
  proposal + specs ──MR (PO, СА)──► Business Ready
2 СА: /sdd-system-design
  system.md ──MR (техлиды, БА)──► Definition of Ready
                              ├──► backend:  /sdd-impl-plan → design + tasks
                              └──► frontend: /sdd-impl-plan → design + tasks
3                                   /opsx-apply → код + тесты (covers: …)
  «Вопросы к upstream» ◄─────────── design.md
  бизнес → БА, контракт → СА; после merge команды делают resync
4                                   /sdd-impl-verify → PASS → merge → /opsx-archive
5 /sdd-initiative-status, /sdd-business-archive (все компоненты готовы)
```

1. **Бизнес-требования (БА).** Агент сначала задаёт уточняющие вопросы, потом пишет proposal и
   бизнес-delta, по компонентам не распределяет. MR в ветке `spec/<id>`, ревью PO и СА.
   Merge = **Business Ready**.
2. **Системные требования (СА).** `system.md`: компоненты, матрица «сценарий → компоненты»,
   схема взаимодействия, контракты, данные, НФТ, миграция. Сценарии на границе компонентов
   идут в `specs/integration/`. MR в ветке `system/<id>`, ревью техлиды компонентов и БА
   (смысл не искажён). Merge = **Definition of Ready**, до него команды не стартуют.
   Маленькая фича на один компонент может идти одним MR, но с ревью и БА, и СА.
3. **Планирование и реализация.** Каждая команда запускает `/sdd-impl-plan <id>` и получает
   `<id>-<component>` с design и tasks. Контракты берутся из `system.md` как есть. Задачи
   и тесты помечаются `covers: <capability>/<scenario>`. Поведение и контракт «на месте»
   не меняют: вопрос записывается в design.md и решается в store, затем все делают resync.
   MR плана до начала кода желателен, для мелочей план и код можно мержить вместе.
4. **Завершение в компоненте.** `/sdd-impl-verify` = PASS: все сценарии из матрицы покрыты
   задачами и тестами, реализация совпадает с контрактами, задачи закрыты. Потом merge и
   `/opsx-archive`: обновляются технические спеки компонента, бизнес-спеки остаются как были.
5. **Закрытие фичи.** `/sdd-business-archive` проверяет, что все компоненты готовы, и вливает
   delta в `specs/` store. **Definition of Done** = этот MR смержен.

## Частные случаи

| Ситуация | Действие |
|---|---|
| Фича только для frontend | change в store всё равно заводится, `system.md` короткий: один компонент, контрактов нет |
| Технический change (рефакторинг, зависимости, инфраструктура) | только в репо компонента: схема `spec-driven` + `skip_specs: true` |
| Техническое поведение компонента (rate limits, логи, внутренний API) | локальные спеки в `openspec/specs/` компонента |
| Баг в бизнес-поведении | код не соответствует спеке → фикс в компоненте. Спека неполна → сначала правка в store |
| Компонент исключён из скоупа | решение PO, СА правит `system.md`, impl-change удаляется через MR |
| Две фичи меняют один контракт | согласование и версионирование контракта на СА |
| Две фичи меняют одну capability | delta ревьюятся вместе; вторую перед archive проверяют `validate --strict` |
| Новый компонент (mobile) | запись в `components.yaml` + схема `impl-mobile` по образцу frontend |

## Правила работы

| Репо | Ветка | Что в MR |
|---|---|---|
| store | `spec/<id>` | бизнес-требования (БА) |
| store | `system/<id>` | `system.md` (СА) |
| store | `archive/<id>` | закрытие фичи |
| компонент | `feat/<id>-<component>` | план и/или код |

- **Один автор на change.** Остальные пишут в комментариях к MR.
- **Перекрёстные ссылки.** В MR компонента: `Upstream: product-specs/<id> @ <commit>`.
  В MR store перечислены MR компонентов.
- **Порядок ревью MR компонента:** proposal → specs → system.md → design.md → код.
- **Archive только после merge**, и в store, и в компонентах.
- **Перед работой — `git pull` store** (скилы делают это сами), при сомнениях — `openspec doctor`.

## CI

`scripts/ci-check.sh` в каждом репо: `openspec validate --all --strict` плюс проверка, что у
каждого impl-change есть `initiative`. Компонентам нужен клон store:

```yaml
sdd:
  image: node:24
  script:
    - npm i -g @fission-ai/openspec@1.14.1
    - git clone --depth 1 "$STORE_REMOTE" ../product-specs
    - openspec store register ../product-specs
    - ./sdd/scripts/ci-check.sh
```

## Метрики

- доля MR компонентов с impl-change, у которого есть `initiative`;
- время Business Ready → DoR (СА) и DoR → первый impl-change;
- число правок требований после DoR, отдельно бизнес (БА) и `system.md` (СА);
- доля сценариев с тестом;
- lead time DoR → DoD.
