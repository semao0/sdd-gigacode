# Процесс разработки по SDD

## Роли

| Роль | Пишет | Отвечает за |
|---|---|---|
| Бизнес-аналитик (БА) | `proposal.md`, бизнес-`specs/` | что и зачем: проблема, скоуп, сценарии WHEN/THEN |
| Системный аналитик (СА) | `system.md`, `specs/integration/`, `contracts/` | компоненты, матрица сценариев, контракты, логическая модель данных, НФТ, порядок выкатки |
| Техлид компонента | ревью `system.md` и `design.md` | реализуемость, архитектура компонента |
| Разработчик | `design.md`, `tasks.md`, код | реализация, тесты, archive impl-change |
| QA | тест-кейсы в Jira | ручные проверки сценариев, трассировка |

**Граница СА и команд:** всё, что видно снаружи компонента (API, события, ошибки, обмен
данными, НФТ), решает СА. Всё, что внутри (таблицы, классы, фреймворки), решает команда.

## Жизненный цикл

```
STORE                                          КОМПОНЕНТЫ
1 БА: /sdd-business-propose
  proposal + specs ──MR (СА)──► Business Ready
2 СА: /sdd-system-design
  system.md ──MR (техлиды, БА)──► Definition of Ready
                              ├──► backend:  /sdd-impl-plan → design + tasks
                              └──► frontend: /sdd-impl-plan → design + tasks
3                                   /opsx-apply → код + тесты (covers: …)
  «Вопросы к upstream» ◄─────────── design.md
  бизнес → БА, контракт → СА; после merge команды делают resync
4                                   /sdd-impl-verify → PASS → /opsx-archive → merge
5 /sdd-initiative-status, /sdd-business-archive (все компоненты готовы)
```

1. **Бизнес-требования (БА).** Агент сначала задаёт уточняющие вопросы, потом пишет proposal и
   бизнес-delta. Требования общие для всех компонентов; кто что делает, решает СА на шаге 2.
   MR в ветке `spec/<id>`, ревью СА.
   Merge = **Business Ready**.
2. **Системные требования (СА).** `system.md`: компоненты, матрица «сценарий → компоненты»,
   схема взаимодействия, контракты, данные, НФТ, миграция. Сценарии на границе компонентов
   идут в `specs/integration/`. MR в ветке `system/<id>`, ревью техлиды компонентов и БА
   (смысл не искажён). Merge = **Definition of Ready**, до него команды не стартуют.
   Маленькая фича на один компонент может идти одним MR, но с ревью и БА, и СА.
3. **Планирование и реализация.** Каждая команда запускает `/sdd-impl-plan <id>` и получает
   `<id>-<component>` с design и tasks. Контракты берутся из `system.md` как есть. Задачи
   и тесты помечаются `covers: <capability>/<scenario>`. Поведение и контракт «на месте»
   не меняют: вопрос записывается в design.md и решается в store, затем все делают resync.
   MR плана до начала кода желателен, для мелочей план и код можно мержить вместе.
4. **Завершение в компоненте.** `/sdd-impl-verify` = PASS: все сценарии из матрицы покрыты
   задачами и тестами, реализация совпадает с контрактами, задачи закрыты. Затем в той же ветке
   `/opsx-archive` (impl-change переезжает в archive; бизнес-спеки остаются как были, локальные
   спеки компонента в `openspec/specs/` меняют только отдельные технические change)
   и merge: один PR на код и archive.
5. **Закрытие фичи.** `/sdd-business-archive` проверяет, что все компоненты готовы, и вливает
   delta в `specs/` store. **Definition of Done** = этот MR смержен.

Каждый шаг - своя ветка от main. Агент коммитит и пушит её (pre-push хук гоняет ci-check),
PR открывает и мержит человек: merge - это решение ревьюера, а не агента.

## Частные случаи

| Ситуация | Действие |
|---|---|
| Фича только для frontend | change в store всё равно заводится, `system.md` короткий: один компонент, контрактов нет |
| Технический change (рефакторинг, зависимости, инфраструктура) | только в репо компонента: схема `spec-driven` + `skip_specs: true` |
| Техническое поведение компонента (rate limits, логи, внутренний API) | локальные спеки в `openspec/specs/` компонента |
| Баг в бизнес-поведении | код не соответствует спеке → фикс в компоненте. Спека неполна → сначала правка в store |
| Компонент исключён из скоупа | решение БА, СА правит `system.md`, impl-change удаляется через MR |
| Две фичи меняют один контракт | согласование и версионирование контракта на СА |
| Две фичи меняют одну capability | delta ревьюятся вместе; вторую перед archive проверяют `validate --strict` |
| Несколько разработчиков на фичу в одном компоненте | один impl-change: общий design, группы задач в tasks.md по подзадачам с ключом Jira и исполнителем. Отдельный impl-change `<id>-<component>-<part>` — только для независимой части со своим design |
| Новый компонент | запись в `components.yaml` + схема `impl-<component>` по образцу backend или frontend |

## Правила работы

| Репо | Ветка | Что в MR |
|---|---|---|
| store | `spec/<id>` | бизнес-требования (БА) |
| store | `system/<id>` | `system.md` (СА) |
| store | `archive/<id>` | закрытие фичи |
| компонент | `feat/<id>-<component>` | план и/или код |

- **Имя change — `<jira-key>-<slug>`** в нижнем регистре: `shop-142-add-promo-codes`. Ключ
  связывает change, ветки и MR с задачей Jira. У impl-change в конце `-<component>`.
  Проверяет `ci-check.sh`.
- **Тест-кейсы QA в Jira строятся по сценариям спек.** После DoR каждому сценарию
  (`#### Scenario`) бизнес-спек и `integration/` соответствует тест-кейс, связанный с историей.
  ID кейса — `<capability>/<scenario>`, тот же, что в `covers:` у задач и автотестов. Шаги и
  ожидаемый результат берутся из WHEN/THEN. QA дописывает в Jira тестовые данные и окружение,
  но поведение там не меняет: неверный сценарий исправляется через MR в store. Пока кейсы
  заводятся вручную; автоматизация — в [TODO](../TODO.md).
- **Агент не закрывает вопросы сам.** Неочевидный сценарий или выбор между вариантами
  агент выносит человеку: вопрос, варианты, рекомендация. Неотвеченное попадает в
  «Открытые вопросы» proposal или system.md с пометкой `[блокирующий]` или
  `[неблокирующий]`, ответ с именем подтвердившего — в «Принятые решения». С блокирующими
  вопросами останавливаются `sdd-system-design`, `sdd-impl-plan` и `sdd-business-archive`.
  `ci-check.sh` выводит такие вопросы предупреждением, но не падает: ветку `spec/` можно
  обсуждать.
- **Один автор на change.** Остальные пишут в комментариях к MR.
- **Перекрёстные ссылки.** В MR компонента: `Upstream: product-specs/<id> @ <commit>`.
  В MR store перечислены MR компонентов.
- **Порядок ревью MR компонента:** proposal → specs → system.md → design.md → код.
- **Archive только после merge**, и в store, и в компонентах.
- **Перед работой — `git pull` store** (скилы делают это сами), при сомнениях — `openspec doctor`.

## Контекст для агента

Спеки описывают поведение по capability, но не продукт целиком. На большом продукте агент
не читает все спеки: он идёт от общего к частному и читает только затронутое.

| Где | Что | Кто ведёт | Кто читает |
|---|---|---|---|
| store, `openspec/specs/business_spec.md` | продукт: назначение, глоссарий, роли и права, таблица доменов | БА | все скилы store, всегда |
| store, `openspec/specs/<домен>/business_spec.md` | домен: зачем, термины, бизнес-правила | БА | propose, system-design, impl-plan — для затронутых доменов |
| store, `openspec/specs/<домен>/func_spec.md` | домен: как capability складываются в сценарии, связи с доменами | СА | то же |
| компонент, `GIGACODE.md` в корне | правила сервиса: слои, библиотеки, ошибки, транзакции, тесты | техлид | агент сам при любой задаче; impl-plan, impl-verify, system-design |

- **Требования — только в `spec.md`.** В `business_spec.md`/`func_spec.md` только контекст,
  которого в спеках нет, иначе одно правило окажется в двух местах и разойдётся.
- **Документы доменов OpenSpec не трогает** (`list`, `validate`, `archive` их не видят). Поэтому
  их обновляет `sdd-business-archive` при закрытии фичи, если она меняла термины, роли или
  сценарии домена.
- **`sdd-business-propose` подтверждает затронутое у человека**: агент ищет capability по
  терминам из глоссария и показывает список «домен → capability» первым вопросом. Пропущенная
  capability — главный риск на большом продукте.
- **Правила сервиса — в контекстном файле агента**, а не в store: это «как», и оно своё у
  каждого сервиса. GigaCode читает `GIGACODE.md` (Claude Code — `CLAUDE.md`, Qwen Code —
  `QWEN.md`, остальные — `AGENTS.md`). Ссылка на него стоит в `context` `openspec/config.yaml`
  компонента. Файл грузится всегда, поэтому он короткий: правила и ссылки на `docs/`.
  Отступление от правила в design.md — только явное, в разделе «Отступления от правил сервиса»;
  иначе `sdd-impl-verify` даёт FAIL. `bootstrap-component.sh` файл не создаёт, только напоминает.
- **Первичное заполнение** для существующего продукта — агентом по коду и документации,
  люди вычитывают.

## Проверки: pre-push и CI

`scripts/ci-check.sh`: `openspec validate --all --strict`, имена change с ключом Jira и
`initiative` у каждого impl-change. Основные проверки делают сами скилы, `ci-check.sh` ловит
то, что сделано мимо них.

**pre-push хук** — основной способ, от DevOps ничего не нужно. `scripts/pre-push.sh` запускает
`ci-check.sh`, если в ветке относительно main менялся `openspec/`; остальные push не
замедляет. Смотрится вся ветка, а не только новые коммиты: сломанное, что уже на сервере,
не проскочит со следующим push.

Каждый разработчик один раз на клон запускает `$SDD_HOME/scripts/dev-setup.sh` (можно сразу
на несколько: `dev-setup.sh ~/work/shop/*`). Он регистрирует store (у компонента клонирует его
рядом по `references`), пишет `git config sdd.home` и подключает хук через `install-hook.sh`:

| В клоне | Что делает |
|---|---|
| хука нет | ставит свой в `.git/hooks` (или `core.hooksPath`) |
| shell-хук, в том числе копия файла из репо (Gradle копирует `.scripts/pre-push`), husky, `.githooks/` | вставляет SDD-блок в начало хука **и в его исходник в репо**: правку в `.git/hooks` сборка затрёт. Исходник надо закоммитить, после этого блок приходит всем через `git pull` |
| lefthook, не-shell хук, хук, который сборка генерирует не копированием | ничего не трогает, печатает, что добавить, exit 1 |

Повторный запуск ничего не меняет. Блок сохраняет stdin git'а для исходной проверки и берёт путь
к SDD из `$SDD_HOME` или `git config sdd.home`. У кого их нет, проверка пропускается, так что
коммитить блок в общий хук безопасно.

Нет `openspec` — хук предупреждает и пропускает. Разово обойти: `SDD_SKIP=1 git push`; `git push --no-verify`
отключает любые хуки, и git это не запретить: main защищает только проверка на PR в CI.
Хук проверяет рабочую копию, поэтому незакоммиченные правки тоже учитываются.

**CI** — если удастся договориться о шаге в пайплайне; начинать проще со store. Компонентам
нужен клон store:

```yaml
sdd:
  image: node:24
  script:
    - npm i -g @fission-ai/openspec@1.14.1
    - git clone --depth 1 "$STORE_REMOTE" ../product-specs
    - openspec store register ../product-specs
    - ./sdd/scripts/ci-check.sh
```

## Метрики

Подробно — что значит каждая, как считать и о чём говорит: [03-metrics.md](03-metrics.md).

- доля MR компонентов с impl-change, у которого есть `initiative`;
- время Business Ready → DoR (СА) и DoR → первый impl-change;
- число правок требований после DoR, отдельно бизнес (БА) и `system.md` (СА);
- доля сценариев с тестом;
- lead time DoR → DoD.
