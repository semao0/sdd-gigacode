Ты в репозитории КОМПОНЕНТА. Бизнес-требования читаются из store (read-only), здесь
пишется только КАК: design.md и tasks.md по схеме компонента (`impl-backend`/`impl-frontend`).

## Неочевидное - спроси
Если ответ не следует однозначно из спек, контекста или слов пользователя (поведение в
неописанном сценарии, выбор между вариантами, противоречие), не выбирай сам. Спроси
пользователя: вопрос, варианты и твоя рекомендация. Решение записывай, только когда
пользователь его подтвердил; не знает ответа - это открытый вопрос, а не требование.
Спросить некого (запуск без человека) - не пиши файлы на догадках: остановись и выведи вопросы.

## 1. Проверки
1. `openspec doctor` - root локальный, reference на store `ok`. Если store не
   зарегистрирован - покажи fix из вывода doctor и остановись.
2. Обнови store: путь берётся из `openspec store list --json`; `git -C <path> pull --ff-only`.
   Устаревший store = неверные требования; если pull не удался - предупреди пользователя.
3. Определи компонент: `context` в `openspec/config.yaml` и поле schema.
4. Прочитай правила сервиса - контекстный файл агента в корне репо (`GIGACODE.md`; у других
   агентов `CLAUDE.md`, `QWEN.md`, `AGENTS.md`). Нет файла - скажи об этом пользователю и
   бери правила из кода.

## 2. Выбор upstream
1. Пользователь назвал бизнес-change -> `openspec show <id> --store <store>`.
   Иначе `openspec list --json --store <store>` и предложи активные changes, у которых
   этот компонент есть в разделе "Компоненты" system.md.
2. **Гейт DoR**: `openspec status --change <id> --store <store> --json` - все артефакты
   готовы, включая `system`, и system.md есть в origin/HEAD store. Нет system.md -
   остановись: системный аналитик ещё не закончил (`sdd-system-design`). В "Открытые вопросы"
   proposal или system.md есть `[блокирующий]` - тоже остановись: назови вопросы и адресата.
3. Если компонента нет в "Компоненты" system.md - скажи об этом и не создавай change,
   пока пользователь не подтвердит (вопрос к СА).
4. Режим: если в `openspec/changes/*/.openspec.yaml` уже есть `initiative.id == <id>` -
   это **resync**, иначе **новый**. По умолчанию у фичи один impl-change на компонент,
   даже если над ней работают несколько разработчиков: задачи делятся группами в tasks.md.
   Отдельный impl-change на часть (`<id>-<component>-<part>`) заводи, только если
   пользователь явно попросил и часть независима: свой design, общих таблиц и
   эндпоинтов с другой частью нет. В его design.md в `## Upstream` укажи соседние
   impl-changes этой фичи и что решено у них.

## 3. Новый change
1. `openspec new change <id>-<component>` (например `shop-142-add-promo-codes-backend`),
   для отдельной части - `<id>-<component>-<part>`.
2. Допиши в конец `openspec/changes/<name>/.openspec.yaml` (ключи не дублируй):
   ```yaml
   initiative:
     store: <store-id>
     id: <upstream-change-id>
   ```
   `skip_specs: true` OpenSpec ставит сам: в impl-схеме нет артефакта specs, бизнес-delta
   живут в store. Проверь: `openspec validate <name>` не ругается на .openspec.yaml.
3. Для `design`, затем `tasks`: `openspec instructions <artifact> --change <name> --json`,
   пиши строго по инструкции. Код проекта изучай, чтобы design был реальным, но код
   не меняй. Для контекста фичи прочитай `business_spec.md`/`func_spec.md` её доменов в store
   (`<store-path>/openspec/specs/<домен>/`).
   Решения design.md следуют правилам сервиса. Отступление от правила - только явное:
   раздел «Отступления от правил сервиса» в design.md (правило, почему, что вместо).
4. Вопросы к бизнес-спеке и к контрактам не додумывай - они идут в "Вопросы к upstream"
   design.md. Каждый вопрос помечай «блокирующий» (без ответа нельзя реализовать или
   принять работу) или «неблокирующий»: sdd-impl-verify валит только блокирующие.
   Адресат: по бизнес-поведению - бизнес-аналитик, по контрактам и разбиению на
   компоненты - системный аналитик.
5. В tasks.md только работа, которую разработчик выполняет и отмечает в ветке до PR.
   Прогон пайплайна на PR и ручная проверка на стенде - не задачи, а чек-лист описания PR:
   иначе verify не даст PASS до merge.
6. `openspec validate <name> --strict`.

## 4. Resync
1. Сравни текущий upstream (`openspec show <id> --store <store>` и system.md) со списком
   сценариев в разделе "## Upstream" design.md и трассировками `covers:` в tasks.md.
   Для system.md используй `git -C <store> log -p -- openspec/changes/<id>/system.md`
   с даты коммита design.md.
2. Покажи diff: добавленные / изменённые / удалённые сценарии и изменения контрактов.
3. После подтверждения пользователя обнови "## Upstream", затронутые разделы design.md
   и задачи. Выполненные задачи (`[x]`) не удаляй: если поведение поменялось, добавь
   новую задачу на доработку.

## 5. Завершение
1. Ветка `feat/<name>`: `git switch -c feat/<name>` от актуального main
   (уже есть - `git switch feat/<name>`;
   незакоммиченные файлы переходят вместе с ней).
   В main не коммить: `git branch --show-current` должен вернуть `feat/<name>`.
2. Коммит `plan: <name>`, `git push -u origin feat/<name>`. Если pre-push хук (ci-check) упал - исправь.
3. PR (план, по желанию вместе с кодом) открывает и мержит человек, ты не мержишь.
   Назови ветку и ревьюеров: техлид компонента.

Дальше реализация - `/opsx-apply` в той же ветке.
