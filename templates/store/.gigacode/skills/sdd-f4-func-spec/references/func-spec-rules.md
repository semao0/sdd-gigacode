# Правила функциональной спецификации

Функциональная спецификация описывает наблюдаемое поведение системы, которое должно появиться или измениться по Improvement. Бизнес-требования (`BR-*`) уже записаны в `business_spec.md`; здесь они раскрываются в поведение системы. Технический план, архитектура и декомпозиция задач сюда не входят.

Правила репозитория (`schema.yaml`, `config.yaml`, шаблон `func_spec.md`) важнее этого файла. Если они противоречат друг другу, следовать репозиторию и написать о расхождении в описании PR.

## Структура

- Скопировать шаблон целиком, сохранить заголовки разделов и их порядок. Не восстанавливать структуру по памяти.
- Разделы, для которых в источниках нет данных, не удалять, а написать: `Нет данных в источниках.`
- В разделе источников указать ключ Improvement, ключ Story и путь к `business_spec.md`.

## Компоненты

- В разделе «Компоненты» перечислить только компоненты системы, которые затрагивает изменение, и что каждый делает в рамках этого изменения. Роли пользователей сюда не писать.
- Компоненты брать из источников: `business_spec.md`, имена папок в `<change>/specs/` (например `motiv3_pg`, `motiv3_pulse`), описание Improvement. Компонент, которого нет в источниках, не добавлять.

## Карточки FT

- Одно наблюдаемое поведение — одна карточка `FT-001`, `FT-002`, … Номера идут подряд с `001`.
- У каждой карточки есть трассировка на один или несколько `BR-*` из `business_spec.md` той же папки. Несуществующие `BR` не указывать.
- Шаги основного потока начинаются со слова «Система». Изменение статуса объекта записывается и в шаге, и в результате.
- Результат требования с приоритетом Must содержит `ДОЛЖНА` или `НЕ ДОЛЖНА`; Should — одно из трёх: `ДОЛЖНА`, `НЕ ДОЛЖНА`, `МОЖЕТ`; Could — только `МОЖЕТ`.
- У Must обязательно есть проверка. У Should и Could она может быть `—`.
- Текст отказа или сообщения пишется в кавычках «…». Если текст неизвестен — `Нет данных в источниках.` и вопрос в «Открытых вопросах».

## Изменения, а не пересказ

- Если в `<spec_root>/specs/<capability>/func_spec.md` уже описано текущее поведение, в карточке указать, что меняется: «Было: … Стало: …». Неизменное поведение не переписывать.
- Каждый `BR` из бизнес-спецификации либо покрыт хотя бы одной FT, либо вынесен в «Открытые вопросы» с причиной.

## Открытые вопросы

Вопрос добавляется только по конкретному пробелу из этого списка:

1. В FT стоит `Нет данных в источниках.` для факта, без которого поведение не проверить: текст сообщения, условие, правило расчёта, поле.
2. `BR` из бизнес-спецификации не покрыт ни одной FT, потому что в источниках нет данных о поведении.
3. Источники противоречат друг другу: описание Improvement, `business_spec.md`, текущий `func_spec.md`. В вопросе указать оба варианта.
4. Источник, на который ссылается Improvement, не открылся: вложение, Confluence.

- В колонке «Основание» — номер FT, `BR` или название источника, к которому относится вопрос. Вопрос без основания не писать.
- Не задавать общих вопросов («нужно ли логирование?», «какие требования к производительности?») и не предлагать улучшения сверх Improvement.
- Не задавать вопросов, ответ на которые есть в источниках.
- Если пробелов нет — таблица с одной строкой из `—`.

## Чего не делать

- Не придумывать шаги, статусы, роли, сообщения, поля данных и интеграции. Нет факта — `Нет данных в источниках.`
- Не добавлять технологии, API и схемы хранения, если источник не зафиксировал их как часть поведения.
- Не копировать бизнес-спецификацию в функциональную.
- Не оставлять плейсхолдеры `{{…}}`, `TODO`, `TBD` — валидатор их не пропустит.
- В таблицах не использовать символ `|` внутри ячеек. Пустую таблицу оставлять с одной строкой из `—`.
