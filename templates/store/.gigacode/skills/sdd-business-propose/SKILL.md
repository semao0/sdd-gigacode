name: sdd-business-propose
description: Бизнес-аналитик - создать или изменить бизнес-change в store (proposal + бизнес-specs; system.md делает системный аналитик, design/tasks - команды). Используй, когда бизнес-аналитик описывает новую фичу, изменение поведения продукта или правку уже открытого бизнес-change, в том числе по вопросам от команд компонентов.
---

Ты работаешь в STORE - отдельном git-репозитории бизнес-спек, общем для всех компонентов.
Результат: change со схемой `business` с готовыми proposal.md + specs/, готовый к ревью через MR.
system.md (компоненты, контракты) пишет системный аналитик скилом `sdd-system-design`;
design/tasks - команды. Код компонентов ты не трогаешь.

## Неочевидное - спроси
Если ответ не следует однозначно из спек, контекста или слов пользователя (поведение в
неописанном сценарии, выбор между вариантами, противоречие), не выбирай сам. Спроси
пользователя: вопрос, варианты и твоя рекомендация. Решение записывай, только когда
пользователь его подтвердил; не знает ответа - это открытый вопрос, а не требование.
Спросить некого (запуск без человека) - не пиши файлы на догадках: остановись и выведи вопросы.

## 1. Подготовка
1. `openspec list --json` - убедись, что root это store (есть `.openspec-store/store.yaml`).
   Если нет - остановись и скажи, что скил запускается в клоне store.
2. `git pull --ff-only` - работать на устаревших спеках нельзя.
3. Режим:
   - **новый change** - пользователь описывает новую потребность;
   - **правка** - пользователь называет существующий change (или приносит вопрос из
     раздела "Вопросы к upstream" design.md компонента). Тогда `openspec show <change>`
     и переходи к разделу 4, правя существующие файлы (раздел 2 - для затронутых доменов).

## 2. Контекст продукта
1. Прочитай `openspec/specs/business_spec.md`: глоссарий, роли, домены. Термины в спеках -
   только из глоссария; новый термин - отдельный вопрос пользователю.
2. Найди затронутые capability, не читая все спеки подряд: по таблице доменов и
   `openspec list --specs --json` выбери домены, затем `grep -ril "<термин>" openspec/specs`
   по ключевым словам фичи (синонимы из глоссария), включая роли, права и уведомления.
3. Прочитай `business_spec.md` и `func_spec.md` выбранных доменов и их спеки
   (`openspec show <spec-id> --type spec`).
4. Список «домены → capability, которые меняем / читаем как контекст» вынеси первым пунктом
   в вопросы раздела 3: пользователь подтверждает его вместе с остальными ответами. Отсутствие спеки не значит, что поведения нет: спеки продукта
   могут быть неполными - спроси пользователя, как это работает сейчас.

## 3. Уточнение (до записи файлов)
Задай пользователю вопросы одним списком, только по тому, чего не хватает:
- какую проблему решаем и для кого, ссылка на задачу в трекере;
- что сознательно вне скоупа;
- негативные сценарии: ошибки, права, пустые состояния, лимиты;
- метрика успеха.
Распределение по компонентам не обсуждай - это вопрос к СА.
Не выдумывай бизнес-правила. Если пользователь не знает ответа - запиши вопрос в
"Открытые вопросы" proposal с пометкой `[блокирующий]` (без ответа СА и команды не могут
начать) или `[неблокирующий]`. Ответ на открытый вопрос в specs не фиксируй: ни
требованием, ни сценарием.

## 4. Создание артефактов
1. Переиспользуй существующие capability из подтверждённого списка (MODIFIED), а не плоди
   дубли. Новую capability клади в подходящий домен; новый домен - только с согласия
   пользователя.
2. Новый change: `openspec new change <jira-key>-<slug>` (схема `business` берётся из config).
   Ключ задачи Jira спроси у пользователя и запиши в нижнем регистре; slug называй по
   бизнес-смыслу: `shop-142-add-promo-codes`, а не `shop-142-promo-api`. Без ключа Jira
   change не создавай - `sdd check` его не пропустит.
3. Для каждого артефакта: `openspec instructions <artifact> --change <id> --json`
   и пиши файл строго по инструкции и шаблону: proposal, затем specs. Артефакт `system` не трогай.
4. `openspec validate <id> --strict` - исправляй, пока не станет valid.

5. Если фича меняет термины, роли или сценарии домена, перечисли это в proposal
   (раздел What Changes): `business_spec.md`/`func_spec.md` обновляются при archive, не сейчас.

## 5. Передача на ревью
0. Пройди "Открытые вопросы" proposal ещё раз и спроси пользователя по каждому. Ответ -
   в "Принятые решения" и в specs. Остались `[блокирующий]` - скажи, что change ещё не
   Business Ready: `sdd-system-design` не стартует, пока на них нет ответа.
1. Ветка `spec/<id>`: `git switch -c spec/<id>` от актуального main
   (уже есть - `git switch spec/<id>`;
   незакоммиченные файлы переходят вместе с ней).
   В main не коммить: `git branch --show-current` должен вернуть `spec/<id>`.
2. Коммит `spec: <id>`, `git push -u origin spec/<id>`.
3. PR в main открывает и мержит человек, ты не мержишь.
   Назови ветку и ревьюеров: системный аналитик.
4. Merge в main = **Business Ready**: дальше СА запускает `sdd-system-design`.
   Командам компонентов стартовать ещё рано.
5. Для правки уже взятого в работу change: перечисли, какие сценарии изменились.
   СА обновляет матрицу в system.md, команды делают resync (`sdd-impl-plan`).

Никогда не делай `openspec archive` в этом скиле - для этого есть `sdd-business-archive`.
