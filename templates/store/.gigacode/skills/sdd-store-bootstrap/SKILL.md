---
name: sdd-store-bootstrap
description: Первичное наполнение store спеками по текущему поведению существующего продукта - по коду компонентов и имеющейся документации (business_spec.md продукта, домены, capability-спеки, integration/, контракты). Используй, когда store только что создан (sdd store-init) или в нём нет спек на часть продукта, и пользователь просит наполнить store, восстановить спеки по коду, описать текущее состояние.
---

Ты работаешь в STORE. Задача: описать продукт КАК ЕСТЬ, чтобы дальше фичи шли обычным
циклом (`sdd-business-propose` → ... → `sdd-business-archive`). Ты не придумываешь, каким
продукт должен быть: источник правды - код компонентов, их тесты и документация.
Код компонентов ты только читаешь.

Спеки пишутся сразу в `openspec/specs/` (без change): это фиксация существующего поведения,
а не изменение. Ревью - обычный MR, отдельный на каждый шаг ниже.

## Неочевидное - спроси
Если ответ не следует однозначно из кода, документации или слов пользователя (баг это или
задуманное поведение, мёртвый код, расхождение backend и frontend, расхождение кода и
документации), не выбирай сам. Спроси пользователя: вопрос, варианты и твоя рекомендация.
Решение записывай, только когда пользователь его подтвердил. Не знает ответа - сценарий в
спеку не пиши, вопрос идёт в отчёт MR (раздел 5). Спросить некого (запуск без человека) -
не пиши файлы на догадках: остановись и выведи вопросы.

## 1. Подготовка
1. `openspec list --json` - root это store (есть `.openspec-store/store.yaml`). Иначе
   остановись: скил запускается в клоне store.
2. `git pull --ff-only`.
3. `components.yaml`: у каждого компонента реальные `repo`, `dir` и `description`
   (не значения из шаблона `gitlab.example.com`). Шаблонные - спроси пользователя и поправь
   первым коммитом шага 2.
4. Репозитории компонентов: `WS = ${SDD_WORKSPACE:-<родитель каталога store>}`, клон
   ожидается в `$WS/<dir>`. Нет клона - подскажи `git clone <repo> $WS/<dir>`, сам без
   согласия не клонируй. В каждом клоне `git pull --ff-only`; запомни `git rev-parse --short HEAD`
   для отчёта.
5. Спроси, есть ли документация вне кода (Confluence, ТЗ, README, Swagger, пользовательская
   инструкция) - пусть пользователь даст файлы или ссылки. Документация уступает коду:
   расхождение - вопрос пользователю.
6. Режим:
   - **с нуля** - в `openspec/specs/` только шаблонный `business_spec.md`: шаги 2-4;
   - **дозаполнение** - часть доменов уже есть: прочитай `business_spec.md` продукта и
     `openspec list --specs --json`, работай только с доменами без спек (шаг 3).
     Существующие спеки не переписывай: их меняют через `sdd-business-propose`.

## 2. Каркас продукта (MR 1)
1. Обзор без чтения всего кода: README, структура каталогов, точки входа (роутеры,
   контроллеры, страницы/маршруты frontend), модели и миграции БД, роли/права,
   конфигурация интеграций. Цель - список пользовательских действий и сущностей.
2. Черновик `openspec/specs/business_spec.md` по шаблону, который уже лежит в файле:
   назначение, глоссарий, роли и права, таблица доменов, общие правила.
   - Термины - языком бизнеса, не именами классов. Одно слово - один смысл; синонимы из кода
     (`Topic`/`Subject`) сведи к одному термину и спроси, какой оставить.
   - Домен - область бизнеса (каталог, оплата, отчёты), а не компонент и не слой кода.
     Обычно 3-8 доменов. Для каждого домена - предварительный список capability
     (`<домен>/<capability>`, kebab-case): одна capability - одна связная группа поведения,
     которую можно поменять одной фичей.
   - Поведение на границе компонентов (запрос frontend → backend, ошибки API, ожидания,
     повторы) - домен `integration` (ведёт СА).
3. Покажи пользователю глоссарий, роли и таблицу «домен → capability» и получи подтверждение.
   Это главное решение скила: от разбиения зависят все дальнейшие фичи. Правки - сразу.
4. Ветка `baseline/product` от main, коммит `specs: каркас продукта`, `git push -u origin
   baseline/product`. MR открывает и мержит человек (ревью: БА, СА). Можно не ждать merge
   и продолжать шаг 3 в ветках от `baseline/product`.

## 3. Домены (MR на каждый домен)
Порядок - как договорились с пользователем; по одному домену за раз.
1. Ветка `baseline/<домен>` от актуального main (или от `baseline/product`, пока он не смержен).
2. Для каждой capability домена найди поведение в коде всех компонентов: обработчики API,
   бизнес-логику и валидации backend, экраны, состояния и сообщения frontend, тесты
   (тест - самый надёжный источник сценария и граничных значений).
3. `openspec/specs/<домен>/<capability>/spec.md` - формат основной спеки, как у соседних
   (`openspec instructions specs --json` даёт правила требований и сценариев):
   ```
   # <домен>/<capability> Specification

   ## Purpose
   <назначение capability, 1-2 предложения>

   ## Requirements

   ### Requirement: <название>
   <Кто> SHALL <что>.

   #### Scenario: <название>
   - **WHEN** ...
   - **THEN** ...
   ```
   - Только наблюдаемое поведение: что пользователь делает и что видит/получает. Без
     эндпоинтов, таблиц, классов и UI-элементов фреймворка (правило `specs` в config).
   - Конкретные значения из кода: лимиты, форматы, тексты ошибок, сортировка, пустые состояния.
   - Негативные сценарии - если они есть в коде: ошибки валидации, отсутствие прав, пустые
     данные, недоступность внешнего сервиса.
   - Чего в коде нет, не пиши. Поведение, похожее на баг, в спеку как требование не попадает:
     вопрос пользователю (раздел «Неочевидное»).
   - Backend и frontend ведут себя по-разному (например, frontend ограничивает длину, а backend
     нет) - вопрос пользователю, какое поведение считать правдой.
4. `openspec/specs/<домен>/business_spec.md` и `func_spec.md` по образцу соседних доменов
   (или `examples/shop` в репозитории SDD): зачем домен, термины домена, бизнес-правила;
   capability домена, сквозные сценарии, связи с доменами. Требования туда не копируй.
5. Сценарии на границе компонентов - `openspec/specs/integration/<capability>/spec.md`
   в том же формате. Пишутся с ветками домена, к которому относятся.
6. Контракты: внешние API компонентов (OpenAPI, AsyncAPI, схемы событий) - в `contracts/`
   в корне store, по одному файлу на API, с `info.version` как в коде (нет версии - `1.0.0`).
   Есть спецификация в репозитории компонента - скопируй её; нет - собери по коду
   (генератор фреймворка, если он есть, иначе вручную по обработчикам) и сверь с вызовами
   frontend. Контракты - зона СА: в ревьюеры MR добавь СА.
7. `openspec validate --specs --strict` - исправляй, пока не пройдёт.
8. Коммит `specs: baseline <домен>`, `git push -u origin baseline/<домен>`. MR открывает и
   мержит человек, ревью: БА (смысл и полнота), СА (integration и контракты), техлиды
   компонентов (соответствие коду). Перейди к следующему домену.

## 4. Проверка полноты
После последнего домена сверь покрытие: каждое пользовательское действие из обзора шага 2
(маршрут frontend, публичный обработчик backend, фоновая задача с видимым эффектом)
попадает хотя бы в одну capability. Непокрытое - покажи пользователю списком: дописать
в домен, завести новый или сознательно оставить вне store (технические детали компонента -
это локальные спеки компонента или `GIGACODE.md`, не store).

## 5. Отчёт
В описании каждого MR и в финальном сообщении:
- источник: `<компонент> @ <commit>` по каждому репозиторию, использованная документация;
- домены и capability, число требований и сценариев;
- вопросы без ответа: поведение, похожее на баг, расхождения компонентов и документации,
  не покрытое спеками - с файлом и строкой кода. Это задачи БА: решение оформляется
  обычным `sdd-business-propose` (баг в коде - фикс в компоненте).
- напоминание: в компонентах без `GIGACODE.md` его пишет техлид, в store правила сервиса не идут.

Не создавай change и не делай `openspec archive` в этом скиле. Не правь код компонентов.
