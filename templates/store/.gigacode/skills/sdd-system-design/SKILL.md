---
name: sdd-system-design
description: Системный аналитик - написать или обновить system.md для бизнес-change в store - какие компоненты затронуты, матрица сценариев по компонентам, контракты интеграций (API/события), логическая модель данных, НФТ, миграция. Используй после согласования бизнес-спеки, когда СА прорабатывает фичу, или когда команды компонентов принесли вопросы к контракту.

Ты помогаешь СИСТЕМНОМУ АНАЛИТИКУ в store. Результат: `system.md` (и при необходимости
delta `specs/integration/...`) в существующем бизнес-change. Бизнес-требования (proposal,
бизнес-specs) ты не меняешь: если они неполны или противоречивы, верни вопрос бизнес-аналитику.

## 1. Подготовка
1. Root - store (`openspec list --json`), `git pull --ff-only`.
2. Выбери change (назван или `openspec list --json`). `openspec status --change <id> --json`:
   proposal и specs должны быть готовы, а бизнес-часть - смержена в main
   (`git log origin/HEAD -- openspec/changes/<id>/proposal.md` не пуст). Иначе остановись:
   бизнес-спека ещё не согласована.
3. Ветка `system/<id>`.
4. Режим **правка**: system.md уже есть - пользователь принёс вопросы из раздела
   "Вопросы к upstream" design.md компонентов или сам меняет контракт.

## 2. Сбор контекста
- `openspec show <id>` - proposal и бизнес-сценарии.
- `components.yaml` - допустимые компоненты.
- Действующие контракты: `openspec list --specs --json` (домен `integration/`),
  `openspec/changes/archive/*/system.md` по тем же capability, действующие контракты в
  `contracts/` в корне store (изменяемый файл копируется в `openspec/changes/<id>/contracts/`).
- Если в рабочей папке рядом лежат репозитории компонентов (`$SDD_WORKSPACE` или
  соседние каталоги из components.yaml), посмотри существующие API (OpenAPI-файлы,
  контроллеры, клиенты) - контракт должен быть совместим с тем, что уже есть.
  Код не меняй.

## 3. Уточнение
Одним списком спроси у СА только то, что нельзя вывести из контекста: какие компоненты
и внешние системы участвуют, sync или async взаимодействие, целевые НФТ (RPS, latency,
SLA), требования ИБ и ПДн, порядок выкатки. Свои варианты предлагай сразу.

## 4. Запись
1. `openspec instructions system --change <id> --json` - пиши system.md строго по
   инструкции и шаблону.
2. Проверь сам: каждый сценарий из specs/ есть в матрице; каждый компонент из
   "Компоненты" встречается в матрице; у каждого контракта перечислены ошибки.
3. Поведение на границе, требующее проверяемых сценариев - delta в
   `specs/integration/<capability>/spec.md`, добавь эти сценарии в матрицу.
4. `openspec validate <id> --strict`.

## 5. Передача
1. Коммит, push, MR в store. Ревьюеры: техлиды всех компонентов из "Компоненты"
   (owners в components.yaml) и бизнес-аналитик (только на отсутствие искажений смысла).
2. Merge = **Definition of Ready**: команды запускают `sdd-impl-plan`.
3. В режиме правки после merge перечисли изменённые контракты и сценарии - командам
   нужен resync (`sdd-impl-plan`).
